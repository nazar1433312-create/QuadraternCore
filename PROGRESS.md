## Найдены и исправлены реальные баги

1. **`CTestNetParams`/`CRegTestParams`** использовали тот же общий хелпер `CreateGenesisBlock(nTime, nNonce, ...)`, что и `CMainParams` — когда туда прописали Quadratern-специфичные `pszTimestamp`/`genesisOutputScript`, testnet/regtest генезисы молча пересчитались на другие значения, а их собственные `assert(hashGenesisBlock == ...)` остались со старыми стоковыми litecoin-хэшами. Раньше не всплывало — ни один тест до `qtrn_stake_commitment_tests` не использовал фикстуру `BasicTestingSetup` (она конструирует все три набора chainparams). Итог — `SIGABRT`, каскадом ломавший все следующие тесты. **Исправлено:** `CMainParams` вызывает 7-аргументный `CreateGenesisBlock()` напрямую, не трогая общий хелпер.
2. **Genesis `nTime=1798348800`** декодировался в **27 декабря 2026**, хотя в coinbase-сообщении написано "27/Aug/2026" — ошибка примерно на 4 месяца при первом вычислении timestamp. Не всплывало, пока не попытались построить блок ПОВЕРХ genesis (`BlockAssembler::CreateNewBlock` — "block timestamp too far in the future", потому что реальное время ещё не дошло до фиктивного будущего genesis). **Исправлено:** `nTime=1787788800` (реальные 27 Aug 2026 00:00 UTC), genesis перемайнен (`nNonce=61421`), merkle root не поменялся (не зависит от времени).
3. **`BlockAssembler::CreateNewBlock()` сам вызывает `TestBlockValidity`** на свежесобранном шаблоне блока — но у шаблона ещё физически не может быть PoS-подписи (её добавляет майнер отдельным шагом позже). Наше правило консенсуса ломало создание ЛЮБОГО шаблона блока, а не только приём готового. **Исправлено:** параметр `fCheckStakeCommitment` протянут через `TestBlockValidity`/`ContextualCheckBlock`, `CreateNewBlock` передаёт `false` (по аналогии с уже существующими `fCheckPOW=false`/`fCheckMerkleRoot=false` там же), реальный приём блока (`AcceptBlock`) — по-прежнему строгий (`true` по умолчанию).
4. **`ComputeStakeSigningHash` хэшировал реальный `nNonce` блока.** PoW-нонс находится майнингом ПОСЛЕ того, как коммит уже прикреплён — то есть подпись, сделанная до майнинга (когда `nNonce` ещё не финальный), переставала совпадать с тем, что валидатор пересчитывает ПОСЛЕ майнинга (когда `nNonce` уже другой). Валидатор не должен ручаться за нонс — это уже обеспечивает сам PoW. Не поймали раньше, потому что все более ранние изолированные тесты сравнивали блоки с одинаковым захардкоженным `nNonce=0` с обеих сторон — баг впервые проявился только на честном PoW-майнинге через `BlockAssembler`. **Исправлено:** `header.nNonce = 0;` перед хэшированием в `ComputeStakeSigningHash`; добавлены регресс-тесты в оба файла (`qtrn_stake_commitment_tests.cpp` и `qtrn_stake_commitment_consensus_tests.cpp`).

Баги 2-4 — хороший аргумент в пользу того, что реальный интеграционный тест через `ProcessNewBlock` стоил вложенных усилий: ни один из них не ловился изолированными юнит-тестами модулей по отдельности.

### Полный адресный индекс — почему отложен на testnet-2

### Исследование адресного индекса и решение о масштабе testnet-1

Проверял, можно ли обойтись без полноценного индекса — просто сканировать текущий UTXO-набор раз в блок. **Тупик:** `CCoinsViewCache::Cursor()` (актуальное состояние цепи в памяти) в этом дереве явно кидает `std::logic_error("cursor iteration not supported")` — итерация по кэшу не поддерживается вообще, а курсор по дисковому слою (`CCoinsViewDB`) отражает устаревший снимок (до последнего flush, который бывает сильно позади текущего типа). Значит полноценный инкрементальный индекс (как `TxIndex`) — не опция для оптимизации, а единственный рабочий путь для "любой баланс может стейкать".

Хорошая новость: нашёл, что `UndoReadFromDisk(CBlockUndo&, const CBlockIndex*)` уже даёт для каждого блока `vtxundo[i].vprevout[j]` — полный `Coin` (адрес+сумма), потраченный каждым входом. Строить свою теневую UTXO-таблицу для дебета не нужно — можно переиспользовать уже существующий undo-механизм Litecoin/Bitcoin. Но `BaseIndex` (образец `TxIndex`) — это всё равно полноценная подсистема: фоновый поток синхронизации, прерывания, resume по locator, двухфазный `Commit()`, подключение в `init.cpp`. По объёму — больше, чем `stake_selection`+`stake_commitment`+`stake_pool` вместе.

**Решение (не согласовано явно, принято по ходу работы — можно пересмотреть):** для testnet-1 намеренно упрощаем масштаб. Веха testnet-1 в `ROADMAP.md` формулируется как "проверить сам факт работы гибридной схемы", не как продакшн-масштабируемость. Реальные PoS-сети (Ethereum, Cardano) тоже бутстрапятся с фиксированного набора genesis-валидаторов, а не с полного адресного индекса с первого дня — это стандартная, а не урезанная практика. **testnet-1 использует небольшой фиксированный список genesis-стейкеров** (см. следующий шаг), полный адресный индекс ("любой баланс может стейкать") — осознанно переносится на testnet-2.

## Уроки из процесса проверки (важно не повторить)

- **Не редактировать файлы репозитория, пока фоновая сборка идёт против того же смонтированного каталога.** Однажды это привело к тому, что Automake посреди `make` заметил, что `Makefile.am` новее сгенерированного `Makefile`, и запустил maintainer-mode пересборку конфигурации — результат стало невозможно проверить по логу.
- **Не редактировать (`sed -i` и подобное) лог-файл, в который ещё пишет живой фоновый процесс.** `sed -i` пересоздаёt файл (новый inode); процесс, открывший файл раньше через `>`, продолжает писать в старый (уже отвязанный от пути) inode — весь дальнейший вывод теряется, а через путь виден только "снимок" на момент правки.
- Итог обоих уроков: дождаться завершения фоновой сборки, ничего не трогая в `~/quadraterncore` и в её лог-файле, и только потом действовать.
- `arith_uint256` не имеет `operator%` (только `+`, `-`, `*`, `/`, сравнения) — модуль считался через `a - (a/b)*b`.
- Проверять только целевой тестовый бинарник (`make -C src test/test_litecoin`) и запускать только свой набор тестов (`--run_test=qtrn_stake_selection_tests`) — намного дешевле по времени/ресурсам, чем полный `make` + весь тестовый набор Litecoin, особенно на нагруженном сервере (в моменте load average доходил до 6.4 на 6 ядрах из-за параллельных задач на сервере).

## Правила на будущее (из этого раунда работы)

- Проверить сборкой + тестами после каждого шага, не совмещая правки с работающей фоновой сборкой.
- Любой новый тестовый файл, который создаёт/подписывает `CKey`, должен использовать фикстуру `BasicTestingSetup` (или наследника) — иначе `ECC_Start()` не вызван, и любой вызов в secp256k1 падает (SIGABRT или segfault — уже дважды наступали на эти же грабли).
- Если фикстура `BasicTestingSetup` используется где-то ещё — держать в уме, что она инициализирует все три набора chainparams разом; при добавлении новой сети/параметров сверять genesis-related asserts во всех трёх классах, не только в том, что реально меняли.
- Реальный сквозной тест через `ProcessNewBlock`/`BlockAssembler` ловит баги, которые изолированные юнит-тесты пропускают (нашёл несколько за этот раунд) — стоит своих усилий, не пропускать этот уровень проверки для будущих консенсус-правил.
- При добавлении новых полей/параметров в существующие функции (как `fCheckStakeCommitment` у `TestBlockValidity`) — искать все call-сайты явно (`grep`), не полагаться на память о том, где функция используется.
